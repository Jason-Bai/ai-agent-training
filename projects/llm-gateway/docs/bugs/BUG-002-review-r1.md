### 2. 关键反例与故障时序核对

1. **维护者改用真实模型，但离线用例仍应通过。**  
   五个消费方已改用测试自建注册表或临时 YAML，没有把生产 `load_registry` 全局替换成恒定成功。默认路径测试复制实际模型模块后独立导入，仍执行真正 YAML 解析。最终 JUnit 中 Mock、真实定义、拒读及符号链接四种隔离副本，各为 **202 passed，runtime_reads=[]**。

2. **维护者 YAML 自身是符号链接。**  
   守卫对受保护路径和待访问路径分别 `resolve()`，覆盖该反例。收集阶段观察器也在映射时解析真实路径。既有原始回执显示该缺口经历正确 Red；最终符号链接矩阵通过。专门的收集阶段负例记录到 `gateway.yaml`，外层断言因此通过，没有把“未观察到读取”误当作守卫有效。

3. **流调用在请求 Task 中开始，却在其他 Task 中关闭。**  
   `AcceptanceMockProvider.stream()` 在调用入口复制独立 Context，回调使用捕获的 Context；没有临时改写共享 Provider 的请求字段。结合实际流执行器的 `anext()` Task 与独立 cleanup Task，归属传递成立。双流、第三 Task 清理反例及最终 Mock 原始记录均支持此判断。

4. **重复订阅或续传偷偷触发第二次生成。**  
   共用场景检查首次 GET 前 pending/零 Attempt，续传序号连续、完成后 204、回放不改变账目，并检查唯一 Attempt。Mock 额外以每 request_id 的实际调用记录核对次数。没有仅凭数据库已有一条记录推断“只调用过一次”。

5. **取消与上游完成竞争。**  
   共用场景允许合法终态竞争，并检查 SSE 末事件、重复取消及账目稳定性。最终真实主模型取消节点实际为 `completed`，备用模型为 `canceled`；没有将前者伪装成成功中止。Mock 两节点实际取消且各关闭一次；pending 取消无 Provider 调用。这与保留受控故障专项的范围一致。

6. **默认 live 跳过掩盖最终未执行真实链。**  
   最终顶层 JUnit 实际包含 **28 个 live 节点，0 skipped**。默认跳过、显式缺 Key 失败属于独立隔离子进程内的预期结果，并被外层测试检查，不能与最终顶层状态混淆。
