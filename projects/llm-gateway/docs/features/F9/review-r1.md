### Findings

**P0 · 已复现 · B 可读取、启动或取消 A 的流。** `src/api/identity.py:74–84` 使用独立路径正则的 `fullmatch` 决定是否检查归属。解码后以换行结束的 `events%0A`、`cancel%0A` 都跳过该检查。实际路由仍能匹配，`src/api/routes.py:89–105,118–131` 仅凭请求 UUID 调用管理器。锁定的 Starlette 1.10.0 将路由末尾编译为 `$`，再使用 `.match()`。[Starlette 对应版本源码](https://raw.githubusercontent.com/Kludex/starlette/1.10.0/starlette/routing.py)

执行者回传的隔离 ASGI/PostgreSQL 实验中，B 用自己的有效凭据访问 A 的 pending ID。`GET .../events%0A` 返回 200，A 的 Trace 变为 completed，Mock 上游进入 1 次。对第二条请求执行 `POST .../cancel%0A` 返回 202，A 的 Trace 变为 canceled，上游进入 0 次。该实验没有使用付费上游。付费绑定沿同一启动路径，预算会归在 A 的请求上。应在实际匹配后的请求处理路径或数据访问处，以已验证的 `agent_id` 和解析后的 `request_id` 联合验证归属，再执行查询、认领或取消。回归应同时核对跨户 404、无数据返回、无生成、无状态变更和无账目。

**P1 · 静态确定 · Chat 流的非终态用量足以触发最终扣款。** `src/providers/streaming.py:41–61` 在验证 `finish_reason` 之前把 model、Usage 和缓存拆分写入 `observed`。若一个仍在生成的增量帧带非空 Usage，解析器明确判它非法，但 `src/providers/deepseek.py:67–68` 把这些值原样附到失败事件。`src/services/streaming.py:395–404,445–449` 将其写入 Attempt，`src/persistence/billing.py:103–109` 随后把此次尝试标为 settled。该帧能证明上游上报过一组计数，不能证明它是本次调用的最终用量。实际效果是形成确定扣款、解除预留，且现有 `resolve` 不接受该 settled 项。

最小验证为本地 Chat 替身仅发一个 `finish_reason=null` 的增量帧，其中带正确模型、输入 10、输出 1、合计 11、命中 7、未命中 3。应保留协议失败和允许保留的诊断信息，账务为 pending，两个成本字段均为 null。修正时应区分**可留在 Trace 的观测值**与**足以证明本次最终费用的上游报告**。同时保留已有“终态实报完整、随后传输损坏”可计价的行为。

**P2 · 静态确定 · 已配置的下一版本涨价未进入可能跨版本尝试的预留。** `src/services/prices.py:130–142` 已找到 `next_version`，但它只影响自动结算的截止时间。预留的最高价仍全部取当前版本。`src/persistence/store.py:164–178` 在取得账户锁之前取报价时间，排队或上游调用均可能跨越生效边界。余额只够按旧价运行时，多个尝试仍可能同时通过，之后跨版本转 pending 也只保留旧价金额。

最小验证为设置相邻的两个固定价版本，后一版本费率为前者十倍，账户只够旧报价，调用可能持续到新版本。核对预留额与上游次数。可用本次最晚调用时间覆盖已知适用版本，按其中最高适用费率预留，或阻止已知无法足额预留的跨界派发。仅在结算阶段转 pending 不能修复准入结果。

**P2 · 静态确定 · 本已具备完整证据的费用会因数据库入账较晚转成待核实。** `src/persistence/billing.py:88,103–106` 先等账户锁，再将写账时的 `datetime.now()` 作为调用结束时间传给 `PriceQuote.cost`。`src/services/prices.py:85–89` 将其用于判断是否跨价。举例而言，上游于 11:59:59 返回最终 Usage，数据库锁到 12:00:01 才释放，本次调用完全发生在同一费率时段，却不会自动结算。延迟持久化恢复走同一逻辑。

最小验证为固定价格边界，在边界前返回终态实报，只让账本事务跨界，与实际执行跨界的对照例区分。应在观察到该尝试的可靠终态证据时记录带时区时间，随证据传入结算及延迟持久化路径；执行时间本身不确定时继续 pending。
