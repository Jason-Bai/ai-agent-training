### 本轮 Findings

**P2-1 · 静态确定 · Chat 流的业务正文校验失败，会丢掉同一帧已经给出的终态计价证据。**

`src/providers/streaming.py:42–57` 已验证 chunk 对象、模型、Usage、缓存拆分和唯一 choice 的索引，但在检查 `finish_reason` 前先要求 `delta.content` 为字符串。如果它是数组，即使 `finish_reason='stop'`，也会立即抛出异常。适配器返回的失败事件有用量、无 `billing_observed_at`，`src/persistence/billing.py:97–112` 因此保留整笔预留，要求人工核实。普通 Chat 路径则在验证消息正文前采集同类终态证据。失败尝试费用应遵循同一证据标准。

**最小验证**：本地 Chat 替身发一个带 `object='chat.completion.chunk'`、配置模型、唯一 `index=0`、`finish_reason='stop'` 的帧。输入 10、输出 1、总计 11、命中 7、未命中 3，令 `delta.content=[]`。预期生成仍以 `provider_invalid_response` 失败，费用按这组终态实报结算，预留解除；再只把 `finish_reason` 改成 null，预期 pending。对照检查 HTTP/SSE、Attempt、两项成本和余额。

**最小修正**：在验证帧身份、模型、用量和 choice 身份后，先采集已识别的上游终态及相应时间，再独立校验正文是否可交付。保留正文拒绝及非终态禁止扣款的行为。

**P2-2 · 静态确定 · `/v1/billing/summary` 把流式中间计数当成已知最终消耗，并漏计未知尝试。**

`src/persistence/billing_query.py:21–27` 只用 `a.input_tokens IS NULL` 统计未知，并无条件累加所有非空计数。首轮修复有意把非法中间帧的 10/1/11 留在 Attempt 供诊断。对只发生一次该调用的 Agent，账本正确显示费用待核实，总览却会返回 `known_subtotal.total_tokens=11`、`unknown_attempts=0`。调用方据此无法看出该次最终 Token 总量也未知。

**最小验证**：沿用 `test_r1_chat_usage_without_done_requires_final_report[False]` 的 wire 输入，在同一 Agent 上查询总览。预期 `real.attempts=1`、`real.unknown_attempts=1`、`real.known_subtotal=null`，Trace 仍可查询到中间观测的 11。另以明确终态实报、仅缺缓存拆分的反例对照：其最终 Token 应计入已知小计，费用仍可 pending。

**最小修正**：按“能否确认本次最终用量”计算总览的已知小计和未知笔数。保留诊断观测、Mock 已知用量，并与“能否确认金额”分别判定。直接排除全部 pending 会损失最终用量已知但费率、模型或分类仍待核实的记录。
