# F10 总验收

整体设计已由用户确认。补充确认要求使用真实模型提供商，费用不作为跳过或缩减理由。使用闭环、并发和持续运行均接真实 DeepSeek 的 Chat 与 Responses，预算与账务继续正常验证。测试方案另行提交确认。

## 1. 目标与边界

基线为 F1—F9 以及 F9-B1，最新全量 2010 通过、含真实 16 例，历史证据保持原样。本项回答三个问题。

1. 操作者能否从空数据库开始，按文档完成两名 Agent 的建号、签发、拨款、调用、续传、取消和费用核查。
2. 超时、备用、重启和未知费用出现时，请求、Attempt、事件及账本能否互相解释。
3. 在记录清楚的单实例单 worker 环境，能稳定承受什么级别的受控并发，持续调用时哪些资源会增长。

交付验收工具、操作手册和报告。真实 Gateway 子进程、独立 HTTP 调用方、真实 PostgreSQL 使用测试专属资源。正常使用、并发与持续运行使用真实供应商；可控协议服务器仅用于必须确定性复现的超时、畸形帧等故障。默认 Mock 零成本逻辑随历史回归验证。

客服 Agent 的业务项目集成、动态 Router、限流、熔断和多实例属于后续需求。当前使用边界仍为本机或隔离网络、单实例单 worker。容量结论只适用本次机器、配置及负载。若尚未取得真实供应商账单，实付对账继续标明未验证。

## 2. 验收链路与职责

~~~mermaid
flowchart TD
    A[隔离空库迁移] --> B[建两个 Agent 签发与拨款]
    B --> C[独立 HTTP 客户端]
    C --> D[Gateway 单 worker]
    D --> E[可控协议上游或显式真实 Provider]
    D --> F[PostgreSQL 请求 尝试 事件 账务]
    C --> G[客户端收到内容 终态及请求 ID]
    E --> H[上游进入次数与终态证据]
    F --> I[独立读取已提交记录]
    G --> J[逐请求核对 形成报告]
    H --> J
    I --> J
~~~

| 参与者 | 输入输出与归属 |
| --- | --- |
| HTTP 调用方 | 使用真实 Bearer 和 TCP，记录请求 ID、事件序号、内容到达和终态。真实接入由 tests/live 中本项用例及辅助承载，确定性故障由 tests/smoke 承载。 |
| 可控上游 | 按固定脚本交付 Chat/Responses，记录调用数、增量和最终 Usage，只替换外部供应商。 |
| 环境及观测工具 | 复用隔离环境建立能力，创建测试数据库、运行管理 CLI、启动 Gateway，基于持有的 PID/句柄采样和释放资源。 |
| 对照核验 | 对比 HTTP/SSE、SQL、账本及可取得的上游记录，输出操作手册、原始回执与报告。 |

接口使用现有契约，故障屏障放在测试引导或上游。客户端与 Gateway 独立运行，以实际断线验证续传。公共接线由集成者负责。数据库停启、进程故障、容量实验和最终全量串行运行，避免宿主资源竞争。

## 3. 三组完整验证

### 3.1 调用方使用闭环

从空测试数据库执行当前 head 迁移，再按同一份手册运行管理 CLI。

- A、B 分别使用真实签发的 Gateway 凭据，核对跨户隔离。
- A 发起普通、结构化和流式请求，按 request_id 查询 Trace、账务。
- 创建流时 pending，首次订阅启动；收到部分内容后断线，原任务继续；重连仅取 after_seq 之后的事件。
- 发起及轮询取消，最终得到 completed、failed、canceled 中的一个终态，对照上游及费用状态。
- 轮换凭据后继续读取原请求；拨款前后余额、预留和结算可复算。

Prompt、Schema、输入和模型逻辑名复用已验收资产。测试方案给出逐步命令与固定数据，手册命令由真实 HTTP/CLI 流程验证。

### 3.2 故障闭环

已有专项目标测试作为回归，再补跨组件操作链。每个故障都核查响应、持久化记录、上游副作用和账务。

| 场景 | 必须核查 |
| --- | --- |
| 主尝试超时、备用成功 | 上游次数和各次尝试关联正确，未知主费用继续预留，生成结果成功。 |
| 普通或流式余额不足 | 在 Provider 调用前拒绝，零上游调用，账目与原因一致。 |
| 断线重连 | 同一请求唯一生成，序号和内容可接续，补读不增加费用。 |
| 取消与完成竞争 | 唯一终态，清理收口，费用按实际证据结算或保留待核实。 |
| Gateway 终止再启动 | 已开始的未终态请求按现有契约收口，pending 保持；未知费用保留，无重复调用或扣费。 |
| 人工核实 | 核费、确认零费用、平台承担可追溯；重复操作幂等，供应商成本与 Agent 扣款分别可核对。 |

任何回归按已确认契约走 Bug 路径，原场景及影响范围修复后复测；业务范围变化返回需求讨论。恢复证据来自进程外上游记录及已提交 SQL。

### 3.3 并发和持续运行

推荐采用以下固定实验安排，具体数据与命令在测试方案中锁定。

- 1、5、10、20 个同时在途的业务请求，每档连续派发 60 秒。使用闭环负载，完成一个再补一个，普通与流式按固定顺序各占约一半，流创建和订阅合并为一笔业务请求。
- 真实主备接入分别使用 Chat 和 Responses，两种协议均参与普通及流式负载。固定 Prompt、输入规模及输出上限，实际增量节奏、耗时及 Usage 由真实上游决定。结果分别按协议与调用方式记录，外部限流及网络故障单独归因。
- 选最高稳定通过的档位持续运行 10 分钟。用户补充确认：正确处理的上游可用性失败不阻断，但必须报告真实端到端成功率；本地存储/内部故障或归因不明仍阻断。若只有单并发稳定，则按单并发执行并如实记录建议范围。单请求档位无法完成正常流程时判失败。
- 停止派发后，等待在途调用完成或按既有期限收口，再核对活跃任务、连接和账目。
- 采样 Gateway RSS、CPU、活跃连接及流任务、数据库大小、请求和事件行数，报告历史 Trace 与事件增长趋势。
- 记录发起和完成吞吐、成功率、按错误码分类的失败、请求耗时及 p50/p95/p99。客户端首次有效文本延迟与服务端 TTFT 分别记录。
- 用户补充确认分层验收。上游与客户端文本不一致、协议/终态错误、跨户、重复生成或扣款和无法收口均为阻断项；若原始上游本身为短答，则独立统计模型质量异常，保留请求和原始证据。普通及结构化功能用例仍检查业务事实。高档位出现可解释的排队或资源不足时记录已观测瓶颈及最高稳定档位，不外推生产 SLA。若需调整连接池等参数，另行提出有依据的优化方案。

## 4. 通过标准

| 方面 | 通过证据 |
| --- | --- |
| 使用闭环 | 手册在空测试库上跑通，有效请求可关联 Trace/Attempt/账务，认证拒绝和跨户访问不产生副作用。 |
| 一致性 | 重复订阅、取消、恢复和人工处置均无重复账；已知费用与独立手算一致，未知明确表达。 |
| 持续运行 | 至少单并发正常场景稳定完成；各阶段结束后活跃任务可收口，终态及账目一致；资源增长和容量边界有实测解释。 |
| 历史回归 | 最终代码完整开启 --run-live，不筛选执行全部用例，无失败/跳过/筛除，真实两条协议实际执行。 |
| 独立审查 | 依项目流程保留实际提示词、基线、差分、报告，最多三轮，无 P0—P2 才验收。 |

报告标注采样地点、时间和运行环境。客户端收到、Gateway 写出、Provider 发出分别按实际观测下结论。Mock、协议替身、真实 Usage 和实际账单的证据分别记录。凭据由本机配置和隔离测试环境加载，报告不保存密钥明文。
