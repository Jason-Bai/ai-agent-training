### 二、独立反例与时序核查

1. **Agent额度满、全局仍有空位，拒绝是否留下全局占用？**  
   `ConcurrencyLimiter.acquire`先完成全局及Agent检查，再同步修改两份计数，中间没有挂起点。Agent拒绝发生在任何写入前；全局与Agent同时满时先报告global。静态检查及执行者提供的边界/争抢测试证据一致。

2. **同Agent换凭据、模型或协议能否绕过额度？**  
   普通/探测身份来自`AgentIdentityMiddleware`查询所得`agent_id`；流式使用已持久化且经过归属校验的Agent。Limiter不按Bearer、模型或Provider分桶。公共场景实际签发第二凭据，并验证跨模型拒绝及另一Agent可执行，没有发现身份绕过路径。

3. **退避期间其他请求占满容量，原请求是否再次准入失败？**  
   普通准入包围整个`_ordinary_attempts`；流式准入位于首次认领，执行器的恢复循环不调用Limiter。普通恢复专项直接观察准入次数和各Attempt占用；普通/流式集成专项证明原请求继续成功、竞争请求429。未发现恢复中重复计数或提前归还。

4. **pending GET被拒绝是否污染原请求？**  
   名额申请位于`claim_stream`之前；拒绝直接退出，未创建生成Trace、Attempt或费用预留。GET本身不属于`RequestContextMiddleware`创建执行Trace的入口。公共测试同时检查SQL状态、开始时间、期限、错误、事件及后续同ID启动，符合只读拒绝契约。日志使用原生成request_id；HTTP访问ID与生成ID没有被混作一次执行记录。

5. **认领提交ACK不确定、建Task失败及Task首次字节码前取消是否泄漏？**  
   认领异常和建Task异常均撤回凭证；认领不确定进入原孤儿恢复路径，不启动Provider。首次运行前取消由完成回调收回，避免依赖尚未执行的`finally`。专项替身包含真实提交后再抛错，未仅模拟“提交前失败”。

6. **数据库已终态或生成Task退出，关闭仍阻塞时是否提前放行？**  
   `_generate`将执行器登记的清理Task及自身交给凭证；`release_when_done`依据Task真正完成释放，不依据`cancel()`、终态或清理超时。现有清理实现登记读取/worker/关闭Task，清理失败阻止后续Attempt。专项测试在关闭实际活跃时检查429，再解除屏障验证归零及容量复用。

7. **迟到清理退出和生成完成回调是否重复释放，或释放替代请求？**  
   管理器先弹出凭证所有权，凭证自身幂等；Limiter还校验字典中的凭证对象身份。清理回调观察异常并等待全部登记Task，未发现负计数或误释放其他请求的路径。

8. **清理快照之后是否可能新增未纳入凭证的关闭Task？**  
   我进一步沿`_work`、`_single_attempt`、`_read_events`及两层`_cleanup`推导该交错。当前产品路径中，worker没有吞取消后继续生成新清理Task的路径；读取Task通过`asyncio.wait`隔离，已启动的内层关闭Task在挂起前登记。未形成当前调用链可达的反例，因此不将其列为Bug。

9. **停止后数据库补写是否永久占位，或把未知费用记零？**  
   普通路径在执行退出时释放，最终存储由原记录路径处理；流式在本地执行和清理结束后释放，延期持久化没有重新取得名额。容量失败样本仍保留未知Usage和pending费用，未发现借释放额度抹平账务未知的证据。
