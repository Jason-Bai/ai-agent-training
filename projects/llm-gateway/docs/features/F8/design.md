# F8 Trace 完整性与诊断查询

> 整体设计已于 2026-11-02 确认。[测试方案](test-plan.md)已确认。

## 1. 目标与边界

内部 Agent 或开发者拿到一次模型请求的 request_id 后，可以定位请求状态、实际尝试过的模型、恢复原因、耗时和已知用量。覆盖普通生成、流式生成和主动模型探测，沿用本机或隔离开发网络的部署范围。F9 使用逐次尝试的实际用量核算费用。

## 2. 最小方案

1. 写入沿用现有生命周期。普通与流式生成继续向 PostgreSQL 写 Request、Attempt 和已有的流式业务事件。主动探测进入同一登记流程，扩展请求表允许的 operation，保存诊断元数据，不保存探测正文。
2. 探测调用前必须确认登记成功。登记失败返回 503/storage_unavailable，上游调用为零。模型超时记录为探测失败。模型已回复但结果持久化无法确认时，返回存储错误，沿用既有持久化核对机制；一次探测最多调用一次 Provider。
3. 恢复决策随原请求保存。区分实际开始的尝试、预检跳过的候选、尝试之间的等待、停止恢复的原因。取消展示已有取消状态变更、清理结果和最终状态，保留已结束 Attempt 自身的结果。
4. 查询从 PostgreSQL 的同一个一致视图选取白名单字段。HTTP 层包装响应，持久化层负责读取，原生成和取消流程继续负责状态变更。诊断日志用 request_id、阶段及适用时的 attempt_no 关联存储错误，即使查询暂不可用也能定位失败环节。

## 3. 查询契约

`GET /v1/traces/{request_id}`，沿用[接口契约](../../contracts.md)已规划的路径。按一个 UUID 精确查询。响应沿用 success、code、data、message 四字段。查到失败或尚在运行的原请求也返回 200，原请求状态在 data 中表达。非法 UUID 返回 422/invalid_request，无记录返回 404/not_found，读取失败返回 503/storage_unavailable。

| data 中的信息 | 语义 |
| --- | --- |
| 请求摘要 | 原 request_id、operation、请求状态、逻辑模型、模板名称和版本、指纹、预算、时间及错误阶段和受控错误码。入口已拒绝的请求可有零次尝试。 |
| attempts | 按 attempt_no 升序。每项包含原因、模型、Provider 与协议、配置与实报模型、状态、结束原因、错误、耗时和 Provider 实际 Usage。只返回已知信息。 |
| 恢复与取消 | 列出候选跳过原因、实际观察到的等待、停止原因以及取消和清理结果。区分上游尝试失败、请求最终失败、传输错误。 |
| 时间 | 请求总耗时从创建到终态，可能包含流请求等待首次订阅的时间。Attempt 耗时沿用自己的起止点。单列可观察的 Provider 调用耗时和恢复等待。流式 TTFT、生成时长及流时长注明网关观察点；客户端实际收到的时刻不可据此推断。 |
| 用量 | 按已回报 Usage 的尝试汇总 input_tokens、output_tokens、total_tokens，列出用量未知的尝试编号。没有任何实报时，小计为 null。未终态时展示截至查询时刻的记录。本地输入估算与实际用量分开。 |

查询覆盖历史记录，缺失的观察值返回 null。返回的字段排除原始输入快照、Prompt、Schema、回答、SSE 正文、凭据和原始异常。范围为单次请求诊断，普通生成的响应契约继续沿用原设计。

## 4. 验收边界

以数据库行、接口返回和上游实际调用次数交叉核对。需要覆盖主失败备成功、取消与终态竞争、零尝试拒绝、探测登记和完成两侧的存储故障、历史缺失值，以及反复查询运行中请求的只读性。旧记录可读，重启后可查，查询不会启动流或新增 Attempt。最终版本执行全量回归并显式启用真实 Provider。具体用例和通过条件在整体设计确认后独立提交。

## 5. 状态与交接

用户先确认探测登记规则，随后确认整体设计及查询路径。测试方案随后获确认，本项已验收通过。此次只建立按 ID 的元数据查询，计费归 F9。
