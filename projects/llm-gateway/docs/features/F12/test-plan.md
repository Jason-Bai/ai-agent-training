> 状态：验收通过（2026-11-03）。最终完整2508通过，含42个真实节点，零失败/错误/跳过；[第2轮独立复核](review-r2.md)APPROVED、P0—P3均为0。首轮两项P2、修复及两轮全量证据完整保留，见第5—7节。

## 1. 范围与通过标准

### 1.1 要证明什么

证明模型组解析、三层配置和迁移正确，Router给出的候选/原因与实际调用一致；普通、结构化、流式使用统一规则，各端点的消息、Token、恢复和账务不串用；路由不改变原并发、取消、期限、seq及终态约束。保留现有`general-primary`、`general-backup`调用名称、必填model及现有成功响应。

不测试F13任务分类、分类模型准确率、自动熔断、动态配置、多实例、随机/权重/最低成本路由、新协议、图像/工具能力或供应商正式账单。也不以本项证明两个独立供应商容灾：当前两条真实协议仍共用DeepSeek。

基线为[F11最终记录](../F11/test-plan.md)与其原始全量2265节点（2242通过、23个真实失败）及6个有界真实补验。原始失败、600秒24%供应商成功率及证据边界保留，不把补验当作另一轮全量。实施前重新收集当前节点并保存映射，不先承诺F12最终节点数。

### 1.2 测试层次与边界

| 层次 | 本项证明 | 不能代替的证据 |
| --- | --- | --- |
| 配置/纯逻辑 | 真YAML解析、严格类型、引用、预算、稳定筛选和原因 | 不证明真实Provider能力 |
| Mock公共API | 确定的选型、调用顺序/次数、HTTP/SSE与生命周期 | 不证明远端协议、延迟或真实Usage |
| 受控协议上游 | 真Adapter出站字节、Schema/Token差异、精确故障及清理 | 本地503不能称为真实供应商503 |
| PostgreSQL与独立Gateway进程 | 跨连接提交、计划/Attempt/事件/账务关联、重启及资源回收 | 不证明多实例协调 |
| 显式真实Provider | 两条真实协议的实际请求、输出、Usage、费用和路由结果 | 不保证供应商每次成功或固定Token数 |

公共功能复用既有[共用验收原则](../../test-plan.md#已确认的共用验收原则2026-11-03)：Mock与真实共用步骤/业务断言，专属留证由各自夹具承担。ENV、Provider与执行范围独立；纯逻辑及故障注入不重复成远端调用。

### 1.3 通过条件

- T01—T28全部设计规则实际覆盖并记录节点映射；Mock、受控上游及本地Gateway正确性检查零失败/错误，不能只报总体通过率。
- 最终对稳定版本完整运行`--run-live`，既有真实节点及容量测试都执行，零跳过/未选中；保留原始返回码、失败数、日志和JUnit，不把外部失败节点改写为pytest通过。
- 沿用用户在F11确认的分层口径：分别报告模型业务成功率、已证实且被正确处理的供应商故障、Gateway错误及未归因问题。真实失败只有上游原始证据、恢复链、终态/事件/账务和资源一致性共同成立，才可作为正确处理外部故障；仅503/504、provider阶段或一次成功重测均不够。
- 两条真实接入的普通、结构化、流式、续传、取消及探测必须具备对应成功/合法终态证据；必要能力缺少成功验证、未归因故障、丢字、错误终态、越权、错误结算或资源泄漏仍阻断。不要求取消竞态中一定赢过已完成事务，但必须有受控取消路径证据。
- 相关回归及一次自检完成，最终独立Agent三维审查无P0—P2及关键证据缺口；最多三轮。供应商故障导致部分原成功断言失败时，保留失败，由独审根据本节证据核实是否满足分层验收，不能自动豁免或降低原断言。

## 2. 用例

### 2.1 固定准备及共同断言

- 业务输入沿用订单A123、充电器故障；使用`basic_text`、`context_answer@1.2.0`及既有售后Schema。Mock普通文本明确包含订单和商品，结构化返回确定合法对象，流式返回可拼接增量及类型化最终结果、合成Usage。真实不固定逐字文本、Token数或费用，只按相同事实、协议和实报Usage验证。
- 测试自建Provider/端点/模型组YAML、独立数据库、临时凭据/价格及随机回环端口。两端点分别覆盖Chat的json_object和Responses的json_schema；端点ID与模型组名刻意不同，防止代码仍直接把组名当端点。增加第三端点仅作本地候选遍历和次数边界，不增加真实供应商。
- 边界按N-1/N/N+1参数化；严格类型分别覆盖0、负数、true、字符串、小数、null、缺失和未知字段。端点能力、计数结果和价格故意设为不同，避免所有候选相同导致错误被掩盖。
- 通过Event/Future或受控协议屏障确定进入Provider、首增量提交、发送前、退避、关闭中及关闭完成等时刻。不靠固定sleep推断竞争，不按返回列表位置关联并发请求，全部按request_id和实际Attempt记录核对。
- 每个HTTP出口检查状态、四字段信封、`X-Request-ID`、必填model及脱敏。普通成功不增加端点/actual_model/attempts；流式POST为202/pending；SSE检查seq及唯一互斥终态，心跳/EOF不算成功。
- 每个调用前拒绝查询新增Provider进入次数、Attempt、费用预留及扣款，必须为零；路由拒绝仅存元信息/受控路由原因，不存原始正文。执行后检查实际Adapter参数、选中端点、账务、全局/Agent名额及生成/订阅/清理任务归零。
- SQL和Trace通过独立连接及只读查询核对，不仅比较程序内存对象。未知Usage和供应商缓存分类保持未知，不按零结算；本地预检Token不冒充供应商计费用量。

## 3. 执行计划、证据与结论

### 3.1 环境、替换边界及隔离

Python3.12、项目依赖和严格警告模式；使用现有PostgresServer、迁移、子进程/回环HTTP及身份签发工具，拥有自己的库/端口/进程。测试无需停启维护者的数据库或Gateway；数据库故障套件串行，不能因为库名不同就并行执行宿主资源故障。

Mock脚本返回确定文本、合法JSON、typed增量/最终结果、合成Usage及明确可恢复/不可恢复异常；受控双协议服务器制造503、429/Retry-After、畸形JSON/SSE、length、缺Usage及指定时刻断流。不得替换被测Router、真实YAML解析器、预算检查、账务事务或Limiter为固定成功响应。不同价格、计数与候选顺序包含正负对照，保证测试自身能发现错选/错算。

真实夹具仅在`--run-live`下读取用户已本机配置的凭据，使用测试自建真实端点/组配置，不依赖维护者当前gateway.yaml绑定。凭据缺失明确失败，不打印Key、不在命令参数、聊天、源码或工件中保存秘密。ENV不决定是否真实；默认离线与测试收集继续受BUG-002外网/私有文件守卫保护。更新历史共用夹具时检查其自动注入规则不会误改F12显式Registry，不靠放开全局守卫解决兼容。
