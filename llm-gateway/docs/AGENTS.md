# docs 文档约定

先遵守项目根目录的 [工作流](../AGENTS.md)。本目录只存放设计、测试方案、实际证据和可复用经验；草案不能写成已实现或已验收。

## 目录

```text
docs/
├── AGENTS.md                 # 本约定
├── architecture.md           # 跨功能职责与流程
├── contracts.md              # 跨功能 HTTP/SSE/Trace 目标契约
├── response-schema.md        # F4 调用方 Schema 完整规则（状态区分设计/实现）
├── test-plan.md              # 跨功能测试层次和原则
├── progress.md               # 功能状态与证据入口
├── templates/                # 设计、测试、代码导读与独立审查提示词模板
├── references/               # 可复用经验与参考，项目 AGENTS.md 只保留引用
├── features/<编号>/          # 每个 Feature 的 design.md、test-plan.md、implementation-summary.md
│   └── optimizations/O<序号>/ # 该 Feature 的独立优化设计、测试与实际证据
└── bugs/                     # 出现 Bug 时建立记录，不预建空文件
```

## 维护规则

1. 每个 Feature 单独建 `features/<编号>/design.md` 与 `test-plan.md`，保留README内容和交付顺序。先给完整推荐方案及必要备选，用户选择后只讨论影响职责、接口和验收的歧义；标明事实、假设和待决定项，不把普通实现细节拆成重复确认。设计确认后再单独确认测试方案，两者确认前不进入Red。并行开发仍分别保留每个Feature的范围、证据和验收。
2. `test-plan.md`（目录根）只放跨功能测试原则；具体用例、运行命令、实际结果与结论写在对应 Feature 的 `test-plan.md`。设计文档只概述验收边界并链接测试方案，不重复维护用例表。
3. Bug 在 `bugs/` 下单独记录现象、已有契约、复现、回归用例、执行证据和结论；需要改变契约时返回需求讨论。Bug 记录不假装成新 Feature。
4. `progress.md` 只记录状态和证据链接；实现后同步受影响的 README、架构或契约。新增文件仅为当前工作需要，勿为未来功能预建目录或空方案。
   实际独立审查完成后，可在对应 Feature 目录保存 `review.md` 原始报告；核实后的处置与验收结论仍写回 `test-plan.md`，区分工具原文与执行者判断。关键测试/启动的原始输出可按需保存到对应事项目录的 `evidence.json`，工件只保存原始输出，验收结论与审查处置写回测试方案，进度文件只保留状态及入口；历史输出未保存则明确缺口，不补造工件。
5. 状态区分“讨论中、待测试方案确认、开发中、待独立审查、验收通过、阻塞”。验收通过须有实际测试结论及独立审查 Agent 的非阻断审查；后续发现问题走 Bug 路线。Mock、本地接口和真实 Provider 证据分别标注，未执行写“未验证”。
6. 模板按实际问题形成闭环：出现新的通用缺口或过时要求时，按“指出缺口 → 判断是否通用 → 最小修改模板 → 同步当前受影响文档 → 对照核验 → 记录来源与结果”处理；没有新证据不重复展开同目的模板评估。已确认的设计或测试范围若被实质改变，回到对应确认节点；纯模板改进不重置已有确认，也不要求无关历史文档批量重写。
7. 改进依据放在当前 Feature 的状态/交接或测试结论中，进度文件只留入口；不要为每次回看另建日志或流程。领域案例、固定数值和特定路由留在 Feature 文档，模板只保留提问方式、必要字段和证据要求。无法证明改进有效时标记待验证，不因模板更完整就声称后续质量已提高。
8. 可复用的操作经验与参考内容放在 `references/` 的独立文件中，并在项目 `AGENTS.md` 末尾的“经验收获”中引用；Feature 验收证据和 Bug 复现过程仍保留在各自目录，经验文档链接原始记录，不重复维护。
9. 已验收 Feature 的独立优化放在 `features/<编号>/optimizations/O<序号>/`，事项编号为 `<Feature编号>-O<序号>`（如 F1-O1）；优化目录使用同一套 `design.md`、`test-plan.md` 和实际完成后才建立的 `review.md`。设计说明关联基线、变化范围与保留契约，测试方案明确基线回归与本项新增验证。沿用新功能工作流，不新增“优化”第三条路径，不占后续 Feature 编号；在 progress 单列状态，原 Feature 验收状态不因优化待确认而改变。新证据在优化目录闭环，不追加进原设计、测试或审查报告；后续优化递增编号，不预建目录。

10. Feature与独立优化均维护同目录implementation-summary.md，使用[代码实现导读模板](templates/代码实现导读模板.md)。在实现稳定、独立审查前完成，代码修复后同步；用真实文件/类/函数组织阅读顺序，链接设计和验收，避免复制完整diff。导读随同源码参与审查；原历史设计/测试/审查工件不因补导读而重写。

11. 调用方共用的完整规则放在 docs 根目录并由 contracts.md 引用，例如 response-schema.md；Feature 设计引用同一份规则，不重复维护白名单。未实现的规则明确标注目标状态，不能仅因规则文档存在就称 API 已支持。能力查询接口是否需要运行时发现另行讨论，不因新增规则文档自动增加路由。

12. 新功能、独立优化和 Bug 的每轮代码审查，使用 [独立审查提示词模板](templates/独立审查提示词模板.md)，执行前在当前事项目录归档 `review-prompt-r<轮次>.md`，内容与实际提交的审查输入逐字一致，不含真实凭据；不覆盖已执行版本、不补造历史提示词。首轮使用不继承实现对话的全新 Agent（本环境 `fork_turns="none"`），不传入实现者私有推理或预设结论；后续轮次由同一审查者复核新差分及影响链，可复用已核实且哈希未变的基线。固定本轮源码、测试和安全配置快照，记录清单/哈希并核对审查前后变化，排除凭据；实际工具能力与只读任务约束分别记录，不把任务约束写成工具强制限制。每项最多三轮完整审查，更换工具不重置轮次；Claude Code 仅为可选工具，历史记录保留原事实。报告和处置按规则 4/9 留存，覆盖需求正确性、实现一致性、系统正确性、独立反例及未验证项；需要实验时记录执行者的原始回执与审查者复核结论。Bug 沿用当前记录所在目录，共用目录时提示词及报告文件名前加 Bug 编号，不为本规则预建目录。

13. 实施步骤写明任务依赖、文件/资源归属和并行边界；仅并行已确认且独立的任务，由统一集成者处理公共接线与迁移，按README顺序交付。开发中保留目标测试和相关回归，稳定集成后执行必要全量；数据库停启等故障套件串行。评估、回归和下一轮审查由实质变更或新证据触发，复用可核实的未变基线，不以减少步骤为由省略关键验证。
