# F10 总验收测试方案

状态为已验收通过。[整体设计](design.md)已确认，补充要求正常使用及容量实验接真实提供商，费用不构成跳过或缩减依据。以下为已确认方案，实际执行记录见文末。

## 1. 环境及共同验收条件

- Gateway 是独立单 worker 子进程，客户端通过真实 TCP 调用；数据库为测试专属 PostgreSQL Compose 实例，真实 Provider Key 由测试加载本机既有文件，仅测试目录可引用，密钥不打印。固定本次源码及安全配置摘要。
- 从空库迁移至当前 head，通过真实管理 CLI 创建 A、B 两个 Agent、签发凭据，并各拨入充足测试预算。测试拨款是隔离账户数据，API 的预留和结算照常执行。
- Chat 对应 DeepSeekProvider，Responses 对应 OpenAICompatibleProvider，实际都访问 DeepSeek。两种调用协议分别有真实证据，不能描述为两个供应商。
- 普通和流式均固定使用 basic_text@1.0.0、订单 A123 的简短文本任务，max_output_tokens=128、timeout_seconds=30。结构化使用已有 context_answer@1.2.0 与有效订单 Schema。流式要求非空增量及正确终态，文本内容用业务事实和结构验收，精确字节比对限于存储和重放同一请求。
- 共同核对四字段 JSON、稳定错误码、请求 ID、跨户隔离；业务请求、Attempt、事件和账目通过 request_id 关联；Provider 凭据和 Gateway 密钥不进入响应、日志或原始回执。
- 用量与费用从真实实报分类和保存的价格快照独立复算。终态用量、缓存分类或价格不足时如实记待核实。无最终证据不按零收费。实际供应商账单单列证据状态。

## 3. 真实模型容量与持续运行

### 3.1 负载安排

1. 单独运行真实容量实验。并发档位1、5、10、20，各持续派发60秒。闭环客户端每个槽位完成一笔后再发下一笔，窗口结束立即停止派发，再等待已有请求到达终态或既有期限收口。
2. 按固定轮转覆盖 Chat普通、Chat流式、Responses普通、Responses流式。各类型分别计数，单并发档位也依次覆盖四种。多个测试Agent均分槽位，并保留跨账户账务核对。
3. 请求使用相同非思考文本任务，输出上限128、总超时30秒。创建和订阅视为一笔流式业务调用，创建耗时与首次有效文本等待分别记录。
4. 选择60秒阶段无 Gateway 故障、上游失败均明确归因且全部收口的最高稳定档位，持续派发10分钟。若没有稳定档位则失败并记录诊断，不能跳过持续运行后判通过。
5. 请求结束和采样必须真实完成，不用提前终止进程清空活跃任务。阶段间回到无在途请求再开始下一档。记录每个窗口实际发起、完成、成功/失败、剩余收口数及超时。
6. 费用不会缩减上述档位、时长或历史live用例。测试预算按充足额度拨入；错误的预留、扣款或预算归属仍属缺陷。

### 3.2 指标与归因

| 指标 | 采集和计算 |
| --- | --- |
| 吞吐 | 分别报告派发窗口内启动率和完整批次完成率，明确分母是否包含尾部收口时间 |
| 延迟 | 每种协议/方式统计样本数、p50/p95/p99及最大值；不足100样本时注明尾分位样本有限 |
| 首文本 | 客户端单调时钟计时，起点为发起普通请求或流首次订阅；流创建另记。Gateway内部TTFT另列，不混用 |
| 错误 | HTTP/SSE分类、来源、Attempt及恢复；Provider限流、上游超时、Gateway存储故障分别列出，不因最终fallback成功抹掉初次错误 |
| 资源 | 每5秒采样自有PID的RSS/CPU、PG连接与活跃会话、数据库大小；阶段前后取请求/事件/账目数与进程内活跃生成数 |
| 一致性 | 逐请求核对互斥终态、事件序号与结算；逐账户核算拨款−已结算−有效预留=可用余额 |
| 增长 | 单列历史Trace和落库事件随请求数的增长；比较在途任务与连接的收口，避免把保留历史数据误判成泄漏 |

采样使用操作系统、自有数据库和测试引导中只读观测，产品不增加测试路由或调参开关。环境记录CPU/内存、系统/Python/依赖、Gateway/PG部署、网络、时间窗口及配置摘要。由外部模型节奏决定的端到端吞吐不能独立解释为Gateway本体极限。

高档位因外部限流或可解释资源饱和而不稳定，可以报告较低的建议并发。用户已补充确认分层验收。跨户、重复调用/扣款、错误终态、无法收口、上游原文与客户端内容不一致是阻断项。容量场景对完整上游原文与客户端文本进行精确比对，已证实原样转发的模型内容质量异常另行统计数量、请求ID与样本；普通/结构化功能用例继续检查业务事实。单并发正常流程须稳定，所选持续运行档位须全部收口且无未解释异常，否则保留未验收状态。

## 分层验收补充确认

用户在收到两次单字符回答的发现后，明确选择“采用分层验收口径”。容量硬验收涵盖转发、终态与账务一致性；模型质量单独统计。所有成功容量调用都比对上游原始文本与客户端文本，Chat 流式以原始增量重建，Responses 流式另对照最终正文，普通分别读取原始响应正文。只有可核查的原样转发才允许计作模型质量异常。任何不一致都阻断。三个纯逻辑/留证回归确保小数元数据、观测失败与凭据脱敏正确；分层反例验证不会把 Gateway 丢字归为模型质量。

前两次开发容量均失败且未完成既定持续窗口，第二次捕获了完成状态下客户端仅收到“订”；原始上游当时未保留，归因仍未知，不回溯认定为供应商故障。第三次定位被观测器的标准 JSON 小数序列化问题污染（Responses流式均被误判失败），已以 Red1/Green2 修正精确序列化和异常隔离，该数据不代表产品容量。

## 上游可用性验收补充确认

首次完整全量为2037 passed / 1 failed（1695.84秒）。唯一失败为持续运行14416笔中8笔 provider_unavailable，实际成功率14408/14416=99.9445%；逐请求终态、账务及活跃任务收口均通过，原断言要求零失败。用户获知实际结果后，明确选择“按正确处理验收并报告成功率”。原失败回执保留，不改写为通过。

最终硬门槛仍包含完整转发、唯一终态、账目及归属一致。持续运行允许的失败仅为 provider_unavailable、provider_rate_limited、provider_timeout、provider_connection_error；HTTP/SSE错误码必须与持久化错误码一致，持久化错误阶段必须是 provider，且窗口中必须存在成功调用。本地存储、请求总超时、内部或归因不明的失败均阻断。探索档位可以记录资源边界，最终选档及持续阶段仍用上述硬标准。成功率按实际请求报告，不称全部请求成功。

补充指标负例先验证旧零失败判定不能接受用户确认的正确上游失败，修正后指标、留证与PG核对器14 passed。原始上游HTTP失败额外记录状态及稳定错误码，不保存响应头或凭据。真实容量配置复用real_registry，恢复上限为总共3次、每模型2次，无fallback_models；本轮既往实际每请求1次是观测结果，不是配置上限。可恢复故障允许在既有策略内重试，不可恢复错误直接失败。此实验测量该配置下的真实成功率，跨模型fallback由F7完整回归另外覆盖。当前重新执行最终完整 --run-live，覆盖更新后的全部测试和观测代码。
