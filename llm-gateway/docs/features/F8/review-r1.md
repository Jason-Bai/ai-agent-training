### Findings 与最小验证

1. **P2，已复现。探测失败终态已提交但确认丢失，会被恢复流程改写故障阶段。** 上游先返回 `provider_timeout`，`finish` 提交失败终态后抛 `StorageUnavailable(uncertain=True)`。HTTP 正确返回 503，随后 GET 和独立 SQL 同时显示 `failed / provider_timeout / finish`，而 `delivery_error_code=null`。上游失败发生在 `provider`，`finish` 是另一次提交确认故障。执行者的本地 PostgreSQL 回执中，可用 ID `7a223a34-165c-4438-a519-2c0c389b5015` 定位。`src/main.py:74–90` 只对 `completed` 区分确认错误，随后 `src/persistence/store.py:222–235` 用内存快照覆盖已有快照。修正应保留数据库中获胜终态的错误及阶段，单独补记确认故障。复测成功、失败两种已提交终态与未提交对照，核对 HTTP、GET、SQL 和调用次数。

2. **P2，已复现。探测在写库时耗尽期限，返回 504/request_timeout。** 执行者分别阻塞 `prepare`、`begin_attempt`、`finish_attempt`、`finish`。四次 HTTP 均返回 504，上游计数分别为 0、0、1、1。设计第 2 节第 2 条明确要求登记无法确认返回 503/storage_unavailable，模型回复后结果无法确认也返回存储错误。`src/services/gateway.py:65–88,234–246,375–379` 将这些写入阶段的期限耗尽映射成普通请求总超时。`tests/integration/test_f8_probe.py:174` 开始的参数化测试固定了这个相反期望。建议按探测所处的实际阶段分类，保留普通请求总期限和探测上游超时行为。用同四个故障点复测，并保留原两协议慢上游对照。

3. **P2，静态确定。运行中或硬停恢复后的 `provider_entered=false` 可能与实际调用相反。** `src/persistence/store.py:144–158` 在调用前把初值 `false` 写库。普通调用在 `src/services/gateway.py:297–304`、流式在 `src/services/streaming.py:414–421` 将内存观测改为 `true`，这时没有对应的数据库更新。查询直接返回数据库列。若此时进程硬停，`src/persistence/store.py:237–245` 仅更新状态与错误，这个 `false` 会长期保留。最小验证是让受控 Provider 进入后等待，读取 GET，对该进程强制退出后重启并再查一次。尚不能从持久证据判断时应返回 `null`，仅在能够确定未进入适配器时返回 `false`；也可持久化肯定观测。保留原取消准入时序。

4. **P2，静态确定。上游回报合法 Usage、回答类型却不受支持时，已知用量被丢弃。** 例如返回同一请求的模型标识和合法 60/25/85，Chat 的消息为工具调用，或 Responses 的输出项为 `function_call`。业务结果应继续判失败。`src/providers/base.py:83–107` 在读取 Usage 前拒绝 Chat 输出；Responses 虽先验证 Usage，却在 `:155–179` 改抛不含元数据的异常。经 `src/services/gateway.py:316–321`，数据库无 Usage，GET 把这次列为未知。现有协议损坏用例对这类输入只断言错误码。建议让已独立通过类型、非负及总和校验的 Usage 随受控错误传递。复测应使用实际协议字节，经 HTTP 查询比对 SQL；另设损坏 Usage 对照，确认仍为未知。

5. **P2，静态确定。流请求创建时的存储故障没有可用 request_id 检索的阶段日志。** `POST /v1/llm/stream` 在 `src/api/routes.py:67–74` 直接调用 `create_pending`。抛 `StorageUnavailable` 后，`src/middleware/request_context.py:45–52` 只设置通用 `storage` 并入延迟队列，错误处理器只生成 HTTP 响应。数据库当时不可读时，无法从日志定位 `create_pending`，违反设计第 2 节第 4 条。最小验证是在该调用抛错，断言 503、Provider 调用为零，并立即用响应头 ID 查捕获日志。建议在对应存储边界记录受控阶段和 ID，并核对同样直接调用存储的认领和取消路径；不记录异常正文。

6. **P3，静态确定。新建的 pending 流也会反复读取完整执行输入快照。** `src/persistence/store.py:54–59` 创建 pending 时没有写入已知的跳过候选元数据，因此每次 GET 均触发 `src/persistence/trace_query.py:33–40` 的历史兼容分支，读取和解码包含消息的快照。响应仍按白名单输出。建议在创建时保存已知的跳过列表，让完整快照回退只服务历史数据。可用 SQL 监听器核对同一新 pending ID 的两次 GET 都不读取 `input_snapshot`。
