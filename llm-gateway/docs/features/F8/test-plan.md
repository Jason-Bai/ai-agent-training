# F8 Trace 完整性与诊断查询 · 测试方案

> [整体设计](design.md)已确认。本方案已于 2026-11-02 获用户确认。状态为验收通过。第 2 节列出预期行为，第 4–6 节记录实际验证和审查处置。

## 1. 验收口径

从真实 HTTP 入口取得生成或探测的 request_id，再请求 `GET /v1/traces/{request_id}`。将返回结果与独立 SQL 读取的 Request、Attempt、流式事件和测试 Provider 的调用记录逐项核对。SQL 按 request_id 关联内部主键读取，不能用被测查询函数生成期望值。真实 Provider 用例核对适配协议、实际收到的响应元数据与已持久化结果；可控超时、竞态和精确调用次数由可计数替身验证。

## 2. 必测场景

| 编号 | 设置和动作 | 通过条件及关键证据 |
| --- | --- | --- |
| 01 普通生成与入口拒绝 | 成功生成一次；另发一个超预算请求 | 成功请求可查模板、版本、指纹、预算、模型和唯一 Attempt，普通响应仍按既有协议。拒绝请求的诊断 GET 返回 200，原请求为 failed，错误位于调用前，Attempt 与 Provider 调用均为零。 |
| 02 主动探测 | 分别安排正常回复、上游超时、未知逻辑模型；另调 /healthz 和不存在的路径 | 有效探测仅调用指定模型一次，operation 为 provider_probe，成功和失败各自可查，SQL 中无探测输入输出正文。未知模型零调用；/healthz 和无关路由均不产生模型 Request。更新原 F5-O1 将探测与存活检查一起断言为零行的旧用例，保留其余隔离断言。 |
| 03 存储故障 | 分别在探测登记前拒绝写入、模型成功后终态保存失败、提交成功但确认丢失时注入故障 | 无法确认登记时返回 503/storage_unavailable，调用计数 0。后两种情况计数 1，数据库不可确认时返回存储错误；恢复后核对实际提交结果，已提交终态不被覆盖，无重复探测或重复 Attempt。用响应头 ID 对照日志阶段和适用的 attempt_no。 |
| 04 恢复与跳过 | 主模型超时后备用成功；同模型退避再试；预检跳过备用；首段文本已提交后上游失败 | 分别核对顺序、原因、实际等待、终止条件与上游计数。跳过的候选不占 Attempt；重试和切换可区分。首段后不再调用，查询保留流失败前已经发生的尝试。 |
| 05 用量 | 固定上游回报 60 输入 + 25 输出；加入一次无 Usage 的超时；参数化全部已知、全部未知、实报零及零尝试 | 混合场景小计为 60/25/85，未知列表仅含超时那次的编号。全部未知和零尝试的小计均为 null，两者可由 Attempt 列表区分。实报零保留为 0。输入估算不计入实际小计。 |
| 06 六态与取消竞争 | 在 pending、running、canceling 的受控停点查询；分别让生成完成、取消或清理失败先落库；取消时已有一次失败尝试 | 可分别读到三个中间态和 completed、canceled、failed 三类终态。每条流仅一个终态事件，清理结果与获胜事务一致，已结束 Attempt 的原始错误不被改写。订阅断开再查询不触发取消。 |
| 07 时间口径 | 分开控制首次订阅等待、登记、上游首段、上游结束、恢复等待与网关流结束 | 总耗时包含创建至首次订阅的等待；已观测的 Provider 耗时排除登记与退避。按已有观察点分别验证 TTFT、生成和流时长；未发生的起止点返回 null。用可控时钟或屏障隔离各段，避免用浮动的网络耗时断言毫秒相等。 |
| 08 HTTP 与只读性 | 查有效 ID、非法 UUID、随机未登记 UUID；在数据库不可读时查一个已进入内存的 ID；重复查 pending 或终态 | 分别验证统一四字段的 200、422/invalid_request、404/not_found 和 503/storage_unavailable。断库时不读内存冒充成功。空闲 pending 请求反复查询后仍为 pending，调用数、Request/Attempt 行数和事件序号均不变。 |
| 09 并发一致性与隔离 | 两个不同 ID 使用不同模型结果，交错完成；将一次查询与写入下一 Attempt 或终态的事务受控交错 | 按 ID 核对无串单。单次响应中的状态、尝试和用量来自同一个已提交视图，例如首次成功终态不能搭配仍在运行的唯一 Attempt。不能仅靠循环碰运气覆盖竞争窗口。 |
| 10 迁移与重启 | 在 F7 版本数据库留下普通和流式记录后升级；新建 F8 探测记录，再重启 Gateway | 旧 request_id 可查，新增且无历史证据的观察值为 null。重启后新旧记录均从 PostgreSQL 读取；原有 pending 与终态恢复规则继续成立，无上游重放。 |
| 11 脱敏 | 用不同哨兵串标记变量、Schema、正文、SSE delta、伪密钥和原始异常，触发成功、失败与存储故障 | 检查实际 HTTP 响应字节、嵌套字段白名单与捕获的诊断日志。哨兵和堆栈不出现，允许的指纹、错误码和关联 ID 可查。不使用真实密钥做泄漏测试。 |
| 12 真实接入 | DeepSeek Chat Completions 与 OpenAICompatible Responses 分别实际发起探测、普通生成和流式生成，拿对应 ID 查询 | 可以复用已有 live 调用增加 GET 断言。每种操作的协议、最终状态、尝试编号及实际回报的用量与数据库相符，查询无正文。两种协议都连接已配置的 DeepSeek 服务。 |

## 3. 执行与留证

1. 设计和本测试方案均确认后，按功能切片做 Red → Green。先确认 F8 节点已收集，再用 `uv run --python 3.12 python -W error -m pytest -k f8 -q` 执行离线目标用例，并定向回归被修改的历史断言。留存关键失败原文、同场景修复回执和故障注入位置。
2. 使用项目已有的隔离 PostgreSQL Compose 测试库执行实际迁移、SQL 核查、事务交错和进程重启。停库、重启等故障场景串行执行。凭据由 live fixture 加载，默认 Mock 配置保持现状。证据只保存必要的脱敏元数据、计数、状态和执行回执。
3. 最终代码从项目根目录运行 `uv run --python 3.12 python -W error -m pytest --run-live -o junit_family=xunit1 --junitxml=<证据目录>/all-live.xml -ra -q`（将占位符替换为本轮实际目录）。全量不加筛选，逐项核对收集清单、JUnit、退出码与真实节点。要求失败、错误、跳过、未选中均为零。
4. 独立审查按项目工作流核对需求、实现与系统影响，最多三轮。若修复改变代码，最终全量结果须对应修复后的版本。验收时在此补录各组结果、原始证据、已知限制和独审结论。各轮实际结果见下文。

## 4. 开发验证记录

第一次全量开启真实调用，1813 项执行中 1811 通过，2 个历史协议用例失败。两例分别通过 DeepSeek Chat 和 OpenAICompatible Responses 适配器连接受控的本地慢上游，使用原探测 10 秒期限。虽然 HTTP 均为 504，把上游超时记成 request_timeout 会误导调用方。修复按实际超时阶段分类，上游耗尽期限时沿既有流程延期保存，数据库操作超时另行记录具体阶段；原用例断言完整保留。另增 4 个存储阶段期限用例，与原两协议及相关期限回归共 24 项通过。[开发及首次全量回执](evidence-development.json)

并发一致性用例在读取请求摘要后、读取尝试前提交并发写事务，检查本次 GET 和下一次 GET 各自的数据。真实进程重启的比较先等待已观察到的投递诊断写入；刚看到终态时，TTFT 等后置观测仍可能尚未写入。Red、Green 与补充回归分阶段运行，不将局部通过数相加为最终结果。

修复版全量于 2026-11-02 完成，1817 项通过，0 失败、0 错误、0 跳过、0 未选中。收集节点与 JUnit 逐项一致。16 个真实调用用例全部通过（DeepSeek Chat 8、OpenAICompatible Responses 8），两条接入使用同一真实服务。安全范围内 149 文件的全量前后摘要一致。[原始执行回执](evidence-all-live-r1.json) · [逐项 JUnit](evidence-all-live-r1.xml)。提交独立审查。

## 5. 独立审查与修复

[首轮原始报告](review-r1.md)判定 BLOCKED，P2 五项、P3 一项。[冻结版本](review-baseline-r1.json)、[首轮差分](review-changes-r1.diff)和[执行者复现实验](review-experiments-r1.json)分别保留需求依据、源码版本和观察结果。

| 发现 | 修正及验证依据 |
| --- | --- |
| 业务失败已提交又丢失确认 | 恢复按已落库的获胜终态和错误阶段核对，只补记迟到的诊断。原始故障脚本重跑，HTTP 为 503，GET 为 failed/provider_timeout/provider，另有 delivery_error_code=storage_unavailable，调用 1 次。 |
| 探测在写库阶段耗尽期限 | 按已确认的探测设计，此种无法确认的存储写入为 503/storage_unavailable，修正此前相反的 F8 测试期望。四个阶段实测调用数为 0、0、1、1，真正的慢上游仍返回 504/provider_timeout。 |
| 登记初始值被解释为已证实未调用 | 已持久化肯定证据返回 true；无肯定证据返回 null。对实际出过文本的流强杀 Gateway，重启后仅有的一次调用不会被误报成确定未进入。 |
| 上游回复被拒绝时丢失合法实报 | 两种真实适配器读取受控本地 HTTP 字节，包括普通与 SSE。不支持的工具结果仍失败，合法的 60/25/85 进入 SQL 和 GET；故意损坏总和时保持未知。 |
| 流创建写库失败无日志 | 创建、认领和取消相关存储边界按原 request_id 关联受控阶段。受控故障核对调用次数和日志，保留零调用与提交不确定的区别。 |
| 新 pending 请求重复读取执行正文快照 | 创建时保存已知的候选跳过元数据。用 SQL 监听验证重复查询不读取输入快照，单独构造缺少新元数据的旧记录验证兼容回退。 |

## 6. 第二轮发现与最后一轮复审

[第二轮原始报告](review-r2.md)关闭了首轮六项具体问题，另发现两项 P2 和一项 P3。执行者使用两个真实适配器向本地受控 HTTP 服务探测，在缺失模型名和模型名包含 U+0000 的四种组合上，从 HTTP、独立 SQL、GET 与调用计数复现并用原脚本复测。修复后均为 502/provider_invalid_response、请求和 Attempt 均为 failed、合法的 60/25/85 保留、调用一次。空值、NUL、孤立代理码点、实报损坏和过大的整数分别检查；合法单次上界之和可以超过 BIGINT。已在 SQL 监听区间执行两次 pending 查询，核对均不读取执行快照。[原始实验](review-experiments-r2.json) · [修复差分](review-changes-r3.diff) · [送审清单](review-baseline-r3.json)。

第三轮送审前的最终全量为 **1904 项通过，0 失败、0 错误、0 跳过、0 未选中，573.26 秒**。包括全部 16 个真实调用节点，两种协议各 8 个，同一真实服务。收集与 JUnit 逐项匹配，测试前后安全范围内 154 项指纹一致。[原始回执](evidence-all-live-r3.json) · [JUnit](evidence-all-live-r3.xml)。

第三轮独审 APPROVED，P0/P1/P2 均为 0，P3 为 1。结论为 **F8 验收通过**。保留一项已复现的非阻断局限：直接注入的自定义 ProviderCallError 携带超过单次 BIGINT 范围的计数时，备用成功后普通生成响应可能对内存异常值求和。F8 GET 和 SQL 准确表达未知尝试与已知小计。当前两条真实适配器均提前过滤这种输入。本轮将其记录为自定义注入接口的已知问题，并保留已独审全量验证版本。[第三轮原始报告](review-r3.md) · [独立复现回执](review-experiments-r3.json)。
